Full stack, explained visually

How a frontend, a backend, a database and the infrastructure under them all fit together into one working app. This guide stays tool-agnostic — it is about the shape of the system, not any one framework.

1What is "full stack"?

A full-stack app is just a few cooperating layers, each with one job. "Full stack" means you can work across all of them, not that you must use any particular framework.

🎨
Frontend

What the user sees and clicks. Turns data into a screen, and clicks into requests.

🧠
Backend

Receives requests, applies the rules of the app, and decides what should happen.

🗄️
Database

Keeps the data safe between visits, so it is still there tomorrow.

This guide is deliberately tool-agnostic: it talks about roles (a UI framework, a relational database) instead of naming one product, so it applies whether you end up using React, Vue, Django, Rails, Postgres or anything else.

4Frontend layer

Everything that runs in the user's browser or app, before a request even leaves the device.

🖼️ Rendering

Turning data into visible HTML: pages, components, lists, forms.

🧩 State

Tracking what the user is doing right now — what is open, selected, typed, loading.

🎨 Styling

Layout, spacing, color, responsiveness — making it usable and consistent.

📦 Build & bundle

Combining and optimizing source files into what the browser actually downloads.

5APIs & communication

The frontend and backend usually run as separate programs. An API is the agreed contract that lets them talk without knowing each other's internals.

Request / response shape

The client sends a request (what it wants, maybe some data). The server sends back a response (a status and, usually, data) — almost always as JSON today.

REST-style vs real-time

Most APIs are request/response: ask, wait, get an answer. Some use webhooks (the server pushes a message when something happens) or websockets (an open two-way channel) for live updates.

Deep dive on methods, status codes, headers and the request/response cycle: see http learing mockups/http-explained.html.

6Backend layer

The program that receives API requests, applies the app's rules, and talks to the database on the frontend's behalf.

🧭 Routing

Matching an incoming request (method + path) to the code that should handle it.

⚙️ Business logic

The actual rules of the app: can this user do this? What should happen next?

🔁 Services

Reusable pieces of logic (billing, email, search) the routes call into.

🕒 Background jobs

Work that should not block the response: sending an email, resizing an image, a nightly report.

7Data & storage

8Auth & security basics

How an app remembers "you are logged in" across many separate requests.

1. LoginUser submits credentials
➜
2. CheckBackend verifies them
➜
3. IssueA session or token is created
➜
4. ReuseSent with every later request
Session-based

The server keeps a record of who is logged in and gives the browser a small id (a cookie) that points to it.

Token-based

The server signs a token (such as a JWT) and hands it to the client, which stores it and sends it back with each request. The server does not need to remember it.

Deep dive on HTTPS and the TLS handshake that keeps all of this safe in transit: see http learing mockups/http-explained.html.
